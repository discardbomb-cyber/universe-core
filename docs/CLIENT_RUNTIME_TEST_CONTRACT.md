## Расширение harness: план следующих сценариев

Предлагается отдельный opt-in sourceSet `sableClientTest`, с серверной fixture и клиентским runner в одном тестовом моде, исключенном из core JAR. Он работает через настоящее соединение с одноразовым dedicated server, а не через FakePlayer. Каждому прогону присваиваются runId, scenarioId, clientRole; ready/observations передаются тестовыми payload через обычную сеть. Сервер начинает сценарий только после ready всех требуемых ролей. Нет ожидания кнопок, мыши или desktop automation.

Клиентская машина состояний: CONNECT → WAIT_LEVEL → WAIT_TRACKING → WAIT_RENDER → BASELINE → DRIVE → CAPTURE → LEAVE_AND_RETURN → ASSERT → REPORT → STOP. Таймаут каждой фазы 30 секунд, общий 180 секунд; внешний supervisor root ограничивает процесс пятью минутами. Состояния и причины отказа пишутся до выхода. Код 0 засчитывается только при наличии полного report.json с ожидаемым числом пройденных сценариев; shutdown/crash/пустой отчет означает отказ.

Начальная сцена: один настоящий Sable sublevel с асимметричной палубой, ступенями, сундуком и четырьмя контрастными угловыми маркерами; отдельные обычные блоки позади дают эталон перекрытия. Сервер держит fixture недалеко от клиента, без других движущихся объектов. Камера закреплена относительно обычной позиции мира, yaw/pitch задаются engine player API на фазе установки. Во время измерения движения телепорты запрещены. Готовность требует не просто регистрации sublevel, а finalized объекта, plot blocks и нескольких последовательных rendered frames.

Тест движения тела: штатные Sable импульс/velocity API, уже проверяемые серверной калибровкой, запускают малое линейное движение и поворот. Клиент пишет renderPose и вычисляет ожидаемую экранную область из camera/projection. Screenshot исходного и движущегося объекта показывает реальную блочную геометрию; harness НЕ рисует поверх тестовый корабль или цветной прямоугольник. Наличие getRenderData и frustum intersection необходимо, но недостаточно: PNG должен содержать контрастные маркеры в соответствующих областях, изменение их положения и правильное перекрытие эталонными блоками. Проверка изображения задается до прогона: минимальная площадь маркеров, допустимое отклонение 8 px и минимум 3 кадра. Без этого frame capture может показать пустую сцену и дать ложный успех. Антиалиасинг/освещение допускают диапазоны цвета, не точное совпадение всего PNG.

Тест LocalPlayer: после setup установить `minecraft.options.keyUp.setDown(true)` на 20 клиентских тиков, затем false; отдельно keyJump один тик. Это programmatic input в тестовом моде, проходящий KeyboardInput/LocalPlayer travel и сетевое движение, не внешняя эмуляция UI. Снимать локальные и серверные позиции, riding/support sublevel и correction события. Всегда освобождать keys при исключении/выходе. Нельзя доказывать работу LocalPlayer серверными setPos или FakePlayer. Наклонная палуба, пассажир и collision — следующие сценарии, не успех минимального smoke.

## Гравитация, tracking и два клиента

Серверная fixture меняет только собственный transient modifier `Attributes.GRAVITY`: vanilla → 0.04 → 0 → восстановление, сохраняя чужие modifiers и исходную базу. Для smoke это тестовая adapter fixture; пока production entity adapter не существует, ее успех не доказывает готовность такого адаптера. Реальную передачу проверять у LocalPlayer A и у remote entity A, видимой клиенту B: значение, собственный modifier ID/amount, момент receipt и отсутствие старого modifier после dimension change/death/rejoin. Timeout после server mutation — 100 тиков. Снимок собственного telemetry packet сам по себе не доказывает vanilla attribute sync: читать живой client entity attribute после штатного packet handler.

Падение измеряется отдельно от атрибута: одинаковые начальные условия, без flight/noGravity/effects/water, лог velocity/position обеих сторон. При нулевом поле допускается сохранение начальной скорости, не требовать неподвижности. Drag/jump не выводятся из формулы a/400 без проверки travel порядка.

Обязательный multiplayer gate: два отдельных Minecraft-процесса A и B, два разных имени/offline UUID, собственные game directories, один dedicated server. A стоит/двигается на fixture, B наблюдает A и корабль. A покидает tracking range и возвращается; затем смена измерения A и возврат. Проверить удаление/повторное появление ClientSubLevel, отсутствие призрака старого UUID, сохранность блоков, согласование pose и remote player, повторный render. Это ловит различия host/client и observers, недоступные integrated singleplayer и server GameTest. Серверный FakePlayer не является настоящим клиентом.

При нуле authenticated accounts допустим isolated loopback dev server с offline-mode и двумя dev identities; он проверяет реальные client networking/render процессы, но НЕ online-mode authentication/session сервера. Конфигурация должна связывать сервер только с 127.0.0.1 и задаваться исключительно в одноразовом каталоге после выбора root. Не менять установленный сервер, launcher или аккаунты. Наличие accessToken CLI в Main не дает authenticated session; dev placeholder, supplied launcher configuration и offline identity не считать авторизацией. Токены/секреты не читать и не писать в отчет. Для online-mode gate нужны две легитимные сессии; при их отсутствии gate остается NOT_RUN, не PASS.

Исходники теперь находятся в `src/sableClientTest/java/dev/heiko/universe/clienttest/`, TOML в ресурсах того же sourceSet. Root выполнил compile и static runtime; границы результата перечислены в начале документа. Точные реальные entry points: `ClientProbeMod`, `ProbeServer`, `ProbeClient`. Нужна регистрация отдельного mod ID `universe_sable_client_test` и sourceSet через ModDev, а НЕ gameTestServer run type. Server — обычный dedicated run, client — обычный client run. Root подключил оба static runs и task `exportSableClientProbeLaunches`; B-run остается будущим предложением.

Зависимости: NeoForge 21.1.251 через addModdingDependenciesTo, Sable 2.0.5 implementation (transitive=false), Companion 1.6.0 compileOnly; runtime Create 6.0.10-280/Ponder/Flywheel/Registrate из существующего Sable profile. Sable включает Veil/Rapier/Companion jarjar. Gson доступен в Minecraft; никаких новых testframework/clientGameTest зависимостей. Не смешивать `sableTest` и `sableClientTest` TOML в одном sourceSet. Не включать новый sourceSet в core jar.

Обязательные system properties для server И client:

```text

-Duniverse.clientProbe.runId=static-smoke-001
-Duniverse.clientProbe.artifacts=<absolute workspace path>/run-client-probe/artifacts
```

runId должен совпадать, содержать 1–64 ASCII букв/цифр/underscore/hyphen. При неверном/пустом runId harness выключен. Отдельные игровые каталоги `run-client-probe/server` и `run-client-probe/client`. Никаких секретов. EULA и disposable directory готовит root в рамках выбранной конфигурации. Guard в source отказывает, если loopback IP и offline mode не заданы явно, мир содержит Sable sublevels или fixture volume занят.

Client program arguments: `--quickPlayMultiplayer 127.0.0.1:25575 --username UniverseProbeA --width 960 --height 540`. Остальные dev launch args предоставляет ModDev; authentication session не исследуется. `NEOFORGE_CLIENT_SELFTEST` не задавать. Настройки first-person/Fancy/GUI hidden при необходимости задаются только в новом client каталоге root, не в установленном Minecraft. Server остается работать до остановки supervisor; client сам вызывает Minecraft.stop после report. Общий supervisor timeout 180 секунд после подключения; внутренний client timeout 120 секунд отсчитывается с первого ClientTick (startup до тика покрывает supervisor).

Fixture: 121 ordinary support blocks на y=80; один Sable plot chunk, девять блоков основания (красный/синий/лаймовый/желтый углы), sea lantern наверху. Native body оседает на платформе без freeze/kinematic API и без тестового reposition во время наблюдения. Требуются 20 server ticks с линейной и угловой скоростями <0.02. После readiness сервер однократно ставит каждого подключенного игрока в spectator и камеру (0,85,-12), yaw=0, pitch=16. Это setup статичного сценария, не доказательство LocalPlayer movement.

Client находит fixture по runId-bearing Sable name, подтверждает finalized, plot states пяти маркеров и наличие render data. После минимум 40 world-render frames сохраняет три PNG с интервалом минимум 20 world frames, через RenderFrameEvent.Post и Screenshot.takeScreenshot. GUI/loading overlay/pause кадры исключаются. Никакой substitute geometry не рисуется. Файлы: `<artifacts>/<runId>/server/report.json`, `/client/report.json`, `/client/frames/static-{0,1,2}.png` и metadata JSON каждого кадра. Sable UUID в обоих reports должен совпасть; серверный `READY` и клиентский `CAPTURED_PENDING_VISUAL_REVIEW` означают лишь подготовленные свидетельства. `visualAcceptance=NOT_EVALUATED` всегда: root обязан проверить настоящую геометрию в кадрах и позже добавить заранее выбранный пиксельный критерий. Captured PNG не приравнивается к visual PASS. Следующие этапы movement/gravity/two-client здесь не реализованы.

Открытые runtime риски: settling контакт с support floor, pose/rotation-point semantics, Sable клиентский finalize timing, освещение и фактическая камера. При нестабильном теле/пустых PNG результат не засчитывать. Сервер удаляет свой sublevel и force-load ticket на ServerStopping; обычная платформа остается только в одноразовом мире. Это не production cleanup и не benchmark. Compile и static runtime выполнены root; это не закрывает перечисленные динамические риски.

### Защиты артефактов и независимая cleanup

Защиты кандидата ниже включены в выполненный static run; фактический клиентский статус — `CAPTURED_PENDING_VISUAL_REVIEW`. Отдельная ручная визуальная приемка root завершена и сохранена в validation.json; результаты следующих сценариев не заявлены.

Root дополнительно передает server/client одну новую случайную строку `-Duniverse.clientProbe.nonce=<16–80 ASCII букв/цифр/_/->`. Этот session nonce не секрет и нужен для корреляции, не authentication. Каждая JVM создает собственный runtimeNonce UUID и runtimeStartedAtMillis. Server атомарно создает новый каталог runId (отказ при любом существующем каталоге) и session.json; client допускается только с совпавшими nonce/runId и manifest не старше 120 секунд. Каждая роль атомарно создает собственный новый каталог и отказывает при restart/reuse. Supervisor сначала дожидается свежего серверного manifest/ready; директории не создавать заранее и старые не очищать для повторного использования runId — выбирать новый runId/nonce.

Reports записываются через временный файл и ATOMIC_MOVE, без fallback при неподдерживаемой атомарности. PNG и metadata создаются только внутри нового role directory, старые имена отвергаются; PNG сначала записывается временно и затем переименовывается атомарно. Reports включают sessionNonce, runtimeNonce, runtimeStartedAtMillis, writtenAtMillis; metadata PNG — session/runtime nonce, capturedAtMillis, endpoint, frame и UUID. Root сверяет freshness с моментом запуска, совпадение server/client Sable UUID и supervisor sessionNonce; runtime nonce разных JVM должны различаться. Выход 0 не критерий успеха.

Клиент проверяет actual Connection.getRemoteAddress: resolved InetSocketAddress, loopback address и порт 25575, перед наблюдением и непосредственно перед каждым capture. Local channel/integrated server, unresolved или внешний endpoint отвергается. Клиентский disconnect/ошибка не дает право переиспользовать каталог.

Cleanup independently пытается removeForceLoadTicket и removeSubLevel, объединяет исключения, не пропускает вторую операцию при ошибке первой. Body/container/ticketOwned остаются до подтверждения обеих очисток. На failed ticks предусмотрены до трех попыток суммарно и еще попытка на ServerStopping; если она неуспешна, владение не стирается. Это ограниченный retry одноразовой fixture, не гарантия удаления после остановки процесса. На нормальном shutdown очистка тоже выполняется независимо. Root проверил эти исправления compile и static run; текущая документационная правка не запускала Java/Gradle.

### Реальная автономная остановка и gravity-stop audit (выполнен root)

`ProbeServer` теперь смотрит только `<runId>/client/report.json`, раз в 20 server ticks. Для остановки нужен терминальный runtime статус CAPTURED_PENDING_VISUAL_REVIEW либо FAILED, совпадающие runId/sessionNonce/fixture UUID, отдельный валидный client runtime UUID и свежие written/runtime-start timestamps. Для CAPTURED дополнительно проверяются три конкретных PNG, их свежесть/непустота и корреляция metadata. Это не пиксельная приемка. FAILED без matching tracked UUID не принимается как завершение; fallback — watchdog. Некорректный JSON не запускает shutdown.

После принятого отчета вызывается штатный `MinecraftServer.halt(false)`; `server/shutdown-request.json` фиксирует причину, nonce, UUID, время. Общий 180-секундный watchdog с ServerStarted также вызывает halt(false) только для проверенного offline loopback test server. Он работает на server ticks; зависший tick/GPU/startup по-прежнему требует внешнего supervisor timeout. Ни stdin/RCON, ни process kill, ни искусственные lifecycle events harness не использует. ServerStarted guard отказа до подтверждения loopback не дает права останавливать произвольный сервер.

Для отдельного opt-in shutdown audit root задает **только серверу** `-Duniverse.clientProbe.gravityStop=true`. `ProbeGravityStop` зависит от настоящего Universe alpha.5 main output и его `LivingGravityLifecycleEvents`; sourceSet runtime должен загрузить также мод `universe`, не только тестовый. Он создает одного настоящего vanilla Pig с NoAI, persistence и invulnerable, регистрирует через `LivingGravityDomain` один transient target gravity modifier 0.04 в подтвержденном world-Y frame. NoGravity не включается. Движение/trajectory, клиенты игроков и sync этим audit не проверяются.

В ServerTick.Pre фиксируется, что token/entry/modifier живы до остановки. На настоящем ServerStoppingEvent с priority LOWEST (после default-priority main cleanup) фиксируются scope entries==0, domain entries==0, isClosed==true, token inactive и отсутствие собственного Universe modifier у того же pig instance. Audit не вызывает domain.close до этих наблюдений. На настоящем ServerStoppedEvent LOWEST проверяются isStopped==true, правильный server thread, пустой scope и отказ нового `open(server, uniqueHost)` именно по stopped lifecycle gate (не из-за повторного host ID или неправильного thread). Флаг stopped не модифицируется. Если open ошибочно принят, audit записывает отказ проверки и только затем закрывает ошибочно созданный domain для гигиены.

Отдельный `server/gravity-stop.json` атомарно обновляется от RUNNING через stopping observations к итоговому `PASSED_REAL_SHUTDOWN_AUDIT` либо FAILED. Он содержит session/runtime nonce, runtime/write/event timestamps, pig UUID, фактические boolean/count assertions, live tick count и ошибки. PASS допустим лишь если setup действительно применился и ownership не исчез до shutdown; смерть/выгрузка pig до остановки не должна маскировать проблему. Root требует итоговый ServerStopped timestamp, а не промежуточный файл. Финальный реальный shutdown audit root выполнен; точные assertions и ограничения приведены в начале документа.
