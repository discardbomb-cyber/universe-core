## Предлагаемое владение

Один lifecycle manager на экземпляр `MinecraftServer`, никаких общих карт UUID между двумя integrated/dedicated серверами. Предлагаемый лимит — 1024 активные регистрации на сервер, конфигурируемый с верхним пределом; повторное обновление существующей регистрации не расходует слот. При превышении отказ происходит до изменения атрибута. Ограничивается число registrations, а не число всех сущностей мира. Неактивные сущности не сканируются ради применения гравитации.

Registration содержит identity конкретного `LivingEntity`, UUID для диагностики, сервер, ключ dimension, подтверждённый host frame, owner token, generation и ссылку на последний установленный Universe modifier. UUID недостаточен: после reload/clone он может соответствовать другому Java-объекту. Смена server/dimension/frame, удаление сущности либо устаревший owner token запрещают update. Один entity — один владелец; второй host получает конфликт, а не перезаписывает поле. Закрытие token идемпотентно; старый token не освобождает новую регистрацию.

Все register/update/release выполняются на главном серверном потоке. Listener проверяет логическую сторону и соответствие сервера. Host из другого потока получает отказ либо явно запланированную серверную операцию с повторной проверкой generation; event callbacks не должны запускать неограниченную очередь. Первая версия отказывает всем `Player`, включая fake players, до отдельной проверки настоящего клиента.

У manager есть собственный заранее зарезервированный namespaced modifier ID, общий для его управляемых сущностей. Удаление разрешено только при доказанном владении текущим modifier: если другой мод заменил объект с тем же ID, запись отмечается конфликтной, чужой modifier не удаляется. Без registration нельзя «чистить» любой встретившийся одноимённый modifier. Base value, `NoGravity`, чужие modifiers, скорость и `fallDistance` не восстанавливаются из старого snapshot.

Host cancellation/profile reload освобождает активные registrations до публикации нового контекста. Старый callback с прежней generation отклоняется. После unload/reload или перехода host делает новый opt-in; автоматической активации по одному UUID/field ID нет. При выключении manager запрещает новые registrations, освобождает старые, затем снимает свои bus listeners/ссылки. Если listeners зарегистрированы один раз на весь мод, они только маршрутизируют к существующему server manager и не создают его на событии остановки.

События не гарантируют обработку при kill процесса; восстановление строится на отсутствии persisted ownership.

Для контролируемого Universe-перехода host вызывает release явно перед backend, не ждёт косвенного player event.

## Transient serialization, reload и clone

Проверен `build/moddev/artifacts/neoforge-21.1.251-sources.jar`, классы `AttributeInstance`, `AttributeMap`, `LivingEntity`, `Entity`, `ServerPlayer`:

- `AttributeInstance.addTransientModifier(AttributeModifier)` добавляет modifier без записи в `permanentModifiers`; `save()` сериализует base и только permanent modifiers. `removeModifier(ResourceLocation)` возвращает boolean, удаляет по ID и отмечает attribute dirty. Нельзя делать bulk `removeModifiers()`.
- `load(CompoundTag)` загружает записанные modifiers как permanent, но не является универсальной очисткой уже существующего live instance. Проверка reload должна создать новую сущность из NBT, а не просто вызвать load на том же объекте.
- `replaceFrom(AttributeInstance)` копирует все `modifierById`, включая transient; `AttributeMap.assignAllValues(AttributeMap)` использует replaceFrom. Поэтому «transient никогда не копируется» неверно.
- `ServerPlayer.restoreFrom(ServerPlayer, boolean)` использует `assignBaseValues`, затем вызывает `EventHooks.onPlayerClone`; это не доказательство невозможности копирования modifiers чужими clone listeners. Существующий transient modifier нельзя объявить безопасным для клиента только по этому коду.
- `Entity.restoreFrom(Entity)` использует save/load NBT при обычной смене dimension с созданием новой сущности; transient modifier в штатном сериализованном пути отсутствует. Старые host registrations всё равно необходимо удалить, не перепривязать к новому instance.
- `LivingEntity.getDefaultGravity()` читает `Attributes.GRAVITY`, но `travel()` имеет специальные ветки движения и slow falling. Lifecycle B не расширяет подтверждённую физику A на swimming/elytra/levitation/flight.

Registry владения не сохраняется в NBT, `SavedData` или copy-on-death attachments. На restart пустой manager — ожидаемый результат. Если в сохранении обнаружен одноимённый permanent modifier без доказательства происхождения, это диагностический конфликт, а не основание молча удалить чужие данные. Миграция ошибочного старого permanent изменения потребует отдельной явной политики.

## Связь с durable Sable transfer

Native block/chest staging probe в [SABLE_TEST_SETUP.md](SABLE_TEST_SETUP.md) и будущий velocity round trip — ограниченное runtime-доказательство. Маркер теста не является stable `ShipId → native UUID/plot` mapping, cleanup одноразового fixture не является rollback, `setDirty()` не является durable barrier. Сохранение V/ω после activation не проверяет passenger roster, чужие BE, connected groups или crash recovery.

До real transfer host освобождает vanilla gravity ownership и переводит переход в закрытое состояние. Новый entity/context не наследует token. Повторная активация допускается только после подтверждённого единственного владельца, валидации frame и успешного разрешения профиля. Потеря ownership не снимает transfer quarantine и не означает commit; независимые state machines не должны разблокировать друг друга по событию dimension change.

Production gates остаются из [SABLE_TRANSFER_RECOVERY.md](SABLE_TRANSFER_RECOVERY.md): durable journal до побочных эффектов; stable/native mapping с эпохой; доказанная изоляция staging; target подтверждён на диске до удаления source; проверенные BE и граф; запрет повторного неопределённого warp и конфликтных экземпляров. Пока эти gates не закрыты на закреплённом backend с crash-injection, перенос остаётся probe. Milestone A/B gravity не меняет этот статус. Sable gravity-компенсация отдельно зависит от native-калибровки IDEA-004 и корректного числа физических подшагов; vanilla transient attribute не является её заменой.

## Четыре проверки следующего milestone

1. **Настоящий моб и ownership конфликт:** A apply/update → чужой modifier меняется → release; effective gravity возвращается к актуальному чужому состоянию. Два owners, полный cap и worker-thread вызов отказывают до изменений; старый token не снимает новую регистрацию. После внешней замены собственного ID cleanup не удаляет чужую запись.
2. **Lifecycle серверного моба:** смерть, удаление, unload/reload из NBT, dimension transition и отменённая попытка перехода. На старом instance нет собственного modifier и manager entry; на новом instance нет автоактивации. Проверить release до штатной остановки и новый сервер в том же JVM без унаследованных registrations. Никакие не-opt-in сущности не меняются.
3. **Сериализация и копирование:** active transient отсутствует в NBT новой сущности; контрольный permanent чужой modifier сохраняется. Отдельно воспроизвести `assignAllValues`/`replaceFrom` и убедиться, что копирование transient распознаётся, а не объявляется невозможным. Для будущих игроков clone/death/End/logout проверять отдельным серверным сценарием, сохраняя запрет player API до пункта 4.
4. **Gate реального клиента и transfer:** dedicated server + настоящий клиент проверяют attribute sync, движение, смену dimension, logout/reconnect и отсутствие старого ownership. GameTest/fake player не закрывают client prediction. При неподтверждённом durable transfer переход получает отказ/карантин без source destruction; только runtime gravity-доказательство не разрешает production Sable-перенос.

Каждый результат фиксируется отдельно: source-confirmed API, реализованный lifecycle, серверный GameTest, настоящий client run и production transfer recovery — разные уровни доказательств. Подтверждены интеграция alpha.5, перечисленные серверные mob GameTest, настоящий shutdown, actual chunk unload/reload, ordinary new-JVM restart fixture и два конкретных canceled-callback сценария с runtime unregister proof. Исторические proposals остаются NOT_RUN; whole-Level API gate BLOCKED_NO_VERIFIED_SAFE_DYNAMIC_UNLOAD_API, остальные перечисленные gates открыты.
