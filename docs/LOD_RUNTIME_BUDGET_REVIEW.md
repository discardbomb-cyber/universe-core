# Проверка LOD и runtime-бюджетов

Дата: 5 октября 2026. Статический анализ текущих исходников; Gradle, Java, JVM-нагрузка и измерения MSPT в этой проверке не запускались. После первичного отчета исправлены только `LodScheduler.java` и его JUnit-тесты; статус тестов должен подтвердить общий запуск основного чата. Числа PLAN §8 — цели, не достигнутые характеристики.

Исправление границ: неизменяемый `LodScheduler.Limits` задает queue/workers/bytes/demand/memberships/subscribersPerKey/cacheEntries. Старый конструктор сохраняется: defaults **4096 demand, 16384 memberships, 256/key, 4096 cache entries**. Абсолютные ceilings: **4096 queued, 64 workers, 1 GiB заявленных bytes, 65536 demand, 262144 memberships, 4096/key, 65536 cache entries**. Отказ subscribe происходит до изменения membership, отмены и поколения; accepted upgrade/retry переносит подписчиков без роста счетчика. Unsubscribe возвращает емкость. Регрессионные тесты покрывают 1000 failed/oversize попыток, 1000 retries/fanout/zero-byte cache cycles, idempotence, upgrade/release и атомарный cache preflight. Отдельные caps не заменяют общий ledger PLAN; история revision/epoch остается контрактом host.

## Реальные ограничения и стоимость

- `LodScheduler` пока не вызывается production-кодом (по поиску ссылок в `src/main/java`). Пределы задаются конструктором; настройки PLAN **2 workers / 128 queued** автоматически нигде не установлены. `poll` резервирует слот, `finish` освобождает его. Отмененный worker занимает слот до acknowledgement; зависший worker способен остановить выдачу задач. Исполнителя, deadline, бюджета **2 мс/тик**, сессионного epoch и lease-cleanup здесь нет.
- Дедупликация работает по ключу и текущей ревизии. Новая принятая ревизия переносит подписчиков и отменяет предыдущий token. `finish` требует именно текущий объект task; повторный/поздний результат после retry или unsubscribe отклоняется. Hysteresis — отдельный экземпляр на viewer/object: вход включительно, выход строго за порогом, непрерывная задержка; связи с подписками адаптер еще не создал.
- При Q ожидающих задачах `subscribe` делает до двух линейных поисков queue (`contains`, `remove`), то есть до **2Q** сравнений, плюс heap-вставку O(log Q) и копию S подписчиков при смене ревизии. При Q=128 это до 256 сравнений; `retry` — до Q и копия S. `finish` теперь сканирует кеш только при byte/entry pressure; preflight и eviction вместе дают **до 2C** lookup-операций в demand под `synchronized`, C≤4096 по defaults, ≤65536 абсолютно. При достаточной емкости полный проход отсутствует. Метаданные активного job: token, Version, Entry, HashSet подписчиков; размер worker snapshot/результата здесь не учитывается.
- Кеш LOD ограничивает заявленные caller-ом bytes (минимум 1), а не фактическую Java heap/GPU память, и отдельно число записей. Default C≤4096, абсолютный C≤65536 даже для zero-byte значений. Проверяются оба ограничения до любого eviction; pinned entries могут дать отказ без частичного вытеснения. Нет TTL, дискового кеша или общего CPU/GPU ledger. Неактивные данные живут до вытеснения; host обязан учитывать реальные payloads и overhead.
- `UniverseNetwork.handleRequest` синхронно генерирует сектор на MAIN. `LazyUniverseCatalog` содержит до **256 секторов**, каждый до 8 систем × (1 звезда + 12 планет + 48 лун + 2 пояса) = **504 тела**; до **129 024 body descriptors** в серверном кеше. Один cold sector: максимум 617 вызовов seed-derivation (1 + 8×77), 8 system descriptors и 504 body descriptors; затем до 8 обращений к спискам при подсчете тел. `system/body` lookup сканирует максимум 8 и 63 элементов соответственно, без обхода галактики. Это метаданные, не terrain generation.
- Endpoint допускает **5 запросов/с на игрока**, тогда как PLAN говорит 4. Глобальное окно ограничивает обработку 100 попытками/с; отклоненные попытки тоже расходуют окно. Нет общей очереди 128 или отправочного byte-ledger. Размеры здесь малы: summary содержит только счетчики. Rate-map ограничен 4096 UUID; sector cache — count-based, не byte-based.
- `SectorSnapshotCache`: 256 count-only snapshots; `snapshots()` копирует до 256 ссылок. Disconnect/смена connection очищаются в `MapClientEvents.afterTick`. Прием сравнивает requestId только с еще сохраненной записью этого ключа; повторный равный ID принимается. World UUID отличается — кеш очищается без проверки ожидаемой сессии.
- `EffectManager.update`: N≤A+R кандидатов (maxActive A, maxCandidatesPerUpdate R), TreeMap-вставки и сортировка O(N log N), до **3N** проверок LOW/MEDIUM/HIGH. Пределы положительные, но верхнего абсолютного cap и общего бюджета Universe нет. Cost units/particles — декларации, не измеренное GPU-время; ожидания/spawn queue отсутствуют.

## Воспроизводимые проблемы для решения основным чатом

1. **Рост demand вне queue/cache bounds — исправлен отдельными caps.** Failed/oversize записи остаются до unsubscribe, но дальнейшие уникальные ключи/UUID отклоняются при лимите. Регрессия `thousandFailuresCannotGrowDemandBeyondCap` использует demand=3, memberships=3 и 1000 запросов без unsubscribe; принимаются только первые три. Fanout отдельно ограничен и протестирован. Host leases нужны для доступности после забытых подписок, а не для ограничения числа записей.
2. **Повторная активация старой ревизии — остается контрактом host.** `LodScheduler.subscribe` проверяет revision только пока существует demand. Testcase: сохранить p/rev2, unsubscribe; запросить p/rev1 — принят и может опубликоваться. После вытеснения snapshot аналогичная потеря high-water requestId в `SectorSnapshotCache.accept`, 22–23. Для изменяемых данных host должен проверять авторитетную revision/epoch; API не хранит неограниченную историю.
3. **Глобальное окно расходуется отказами.** `UniverseNetwork.ServerState.allow`, 116–118: один UUID отправляет 100 слишком частых запросов после первого разрешенного; следующий добросовестный UUID в том же окне получает отказ. Разделить защиту от входного flood и глобальный бюджет полезной обработки. Это endpoint availability, не доказательство неограниченной генерации.

## Профили поверхности и gravity ownership

`PlanetPhysicsResolver.resolve` выполняет три Map.get и проверки ID; terrain/surfaceBinding не разрешает. `PlanetRegistry.find` — lookup; `definitions/snapshot` копируют до 5000 по умолчанию (максимум 65536), snapshot дополнительно проверяет уникальность: не помещать их в entity/job tick. Будущий surface adapter должен передавать согласованный immutable профиль и revision/epoch в LOD key, а не читать live registry/чанки worker-ом.

`GravitySampler` O(1). `LivingGravityAdapter.apply` создает временный AttributeInstance и копирует M чужих modifiers: O(M) на зарегистрированного моба, M кодом не ограничен. Owners≤1024, но сильные ссылки требуют release. IDEA-005 B lifecycle пока отсутствует по контракту адаптера; release после смены сервера возвращает WRONG_SERVER, поэтому ownership нужно завершить до переноса либо отдельным host cleanup. LOD eviction не должен снимать gravity у живой сущности; host registrations и transfer epoch имеют отдельного владельца. Игроки адаптером явно отклоняются.

## Три интеграционных измерения после адаптеров

1. **Настоящие поверхности:** cold/warm chunk generation двух планет, фиксированный маршрут через границы регионов и обратный порядок генерации; десять разошедшихся игроков, затем сближение. Записать chunk-generation latency, queue/wait/cancel counts, peak snapshot+cache bytes, allocations и p95/p99 main-thread времени Universe/общего MSPT. Проверить швы, правки после restart и ограничение спроса.
2. **Кеш и переходы Sable:** реальное тело разрешенного размера, 20 смен измерения и 100 колебаний LOD-порога; late result предыдущего transfer epoch. Записать стоимость capture/apply/native transfer отдельно, память до/после ухода, активные owners/leases и сохранность блоков. Существующий test scan непустых секций читает **4096 block states на секцию**, плюс entities уровня; его время нельзя выдавать за production transfer cost или масштаб миллиона блоков.
3. **Сетевая карта и клиент:** warm/cold 256→257 секторов, reconnect, ограниченный burst нескольких игроков, реальные меши/Photon backend после появления. Измерить bytes/sec, обработку MAIN, время snapshot copies, GPU upload/frame и освобождение памяти. Проверить shared CPU cap 128 MiB, GPU cap 128 MiB и отсутствие чужой сессии/устаревшего профиля. До реализации этих адаптеров результаты unit-тестов не закрывают эти бюджеты.
