# Перенос Sable: сохранение идентичности и восстановление после сбоя

Дата: 4 октября 2026 года. Статус: проект протокола, без реализации, сверенный с [исследованием переноса](SABLE_TRANSFER_RESEARCH.md). Исследование API/байткода не включало игровые переносы; этот документ также не объявляет протокол испытанным. Наличие метода переноса само по себе не доказывает атомарность, сохранение UUID, работоспособность block entities или возможность отката.

## Что требуется доказать у backend

Проверяется конкретная сборка Minecraft 1.21.1, NeoForge, Sable и выбранного дополнения с зафиксированными версиями и SHA-256. Термин `WarpSubLevel` относится к стороннему Dimensional Sable, а не автоматически к официальному API Sable. В README дополнения описаны перенос подключённых объектов, исправления позиционных/UUID-ссылок block entities и известные ограничения механических поршней. Это свидетельство необходимости проверки совместимости, а не гарантия сохранности [README Dimensional Sable](https://github.com/hollow-egg/Dimensional-Sable).

Результат исследования должен ответить: когда исчезает source, создаётся ли target с новым UUID/plot, кто сохраняет каждый объект, есть ли подтверждение завершённой записи и какие побочные действия выполняются до возврата метода. Отдельно проверяются исключения после частичного переноса и способ перечисления объектов в сохранениях. Пока ответы неизвестны, допускаются только испытания копии мира. Нельзя вызывать обратный warp и называть это rollback: повторный перенос может повторно преобразовать NBT, сменить идентификаторы и затронуть связанные объекты.

### Установленное исследованием и решение о допуске

| Backend | Установленное свойство | Решение протокола |
| --- | --- | --- |
| Sable 2.0.5, закреплённый commit `6966d2928340de7631abcecf8549904b877df0a8` | Публичные allocation, plot save/load и userData API; отдельная транзакция changeDimension не установлена | Собственный `SablePlotTransferBackend` — кандидат для прототипа, не готовая гарантия |
| Dimensional-Sable 1.0.5, commit `bb2211cfbb7af150245891276d79170e60d80c31` | Публичный Warp переносит connected chain; новые UUID; результат — число участников, без карты UUID; userData явно не копируются | Прямой Warp не допускается; стабильную привязку после сбоя нельзя вывести из результата |
| SablePortLibrary JAR 1.0.0, SHA-256 `ac69ad5b293b3339110c9ab049fb4e16934afa0e280d94cc0f262309a7bea9d0` | Native UUID сохраняются, plot меняется; сущности удаляются до поиска slots, source — до allocate/load target; ошибка загрузки не гарантирует полный отказ | Прямой `teleportFamily` не допускается: нарушен запрет разрушения source до подтверждения target |

Эти выводы приняты из анализа закреплённых артефактов в исследовании, без собственной runtime-проверки. Первичные основания: [контейнер Sable](https://github.com/ryanhcode/sable/blob/6966d2928340de7631abcecf8549904b877df0a8/common/src/main/java/dev/ryanhcode/sable/api/sublevel/SubLevelContainer.java), [WarpSubLevel](https://github.com/hollow-egg/Dimensional-Sable/blob/bb2211cfbb7af150245891276d79170e60d80c31/src/main/java/dev/egg/SubLevelWarper.java), [переносчик SablePortLibrary](https://github.com/jbookout98/sableportlibmod/blob/d0f4912a1d5661cc3be6f18aaddf85afcdac80c2/src/main/java/com/sableport/mod/teleport/SubLevelDimensionTeleport.java). Последний source новее JAR; порядок разрушительных операций исследование отдельно подтвердило байткодом JAR. Документ не предполагает исправленность опубликованного артефакта по новому source.

Рекомендуемый собственный прототип использует отдельный native UUID для staging target, чтобы source и target не конфликтовали в глобальных индексах. Этот UUID может остаться постоянной новой native-привязкой: возвращать прежний UUID не требуется. `ShipId` сохраняется. Пока безопасная изоляция staging и подтверждение записи не проверены, backend не допускается к игровому переносу. Изменение стороннего переносчика требует отдельной проверки API и условий использования, а не внешней обёртки вокруг прежнего разрушительного вызова.

## Инварианты

1. `ShipId` Universe неизменяем и не равен native UUID. Смена измерения, plot и native UUID меняет привязку, а не идентичность корабля.
2. Для одного `ShipId` одновременно разрешён максимум один активный объект. Во время неоднозначного восстановления разрешено ноль; две физические копии могут оставаться в карантине без взаимодействий.
3. Universe не уничтожает source до подтверждённого устойчивого target. Если сам backend удаляет source раньше такого подтверждения, он не соответствует протоколу; дополнительный журнал не исправляет это свойство.
4. Перенос не считается завершённым по успешному возврату функции, появлению меша или наличию объекта в памяти.
5. Неполный журнал, неизвестная схема, конфликт владельцев или недостаточное доказательство приводят к `BLOCKED`, без повторного warp, выдачи груза и автоматической очистки.

«Запрет дубликатов» означает запрет двух доступных игрокам владельцев одного состояния. Отсутствие лишних файлов на диске не обещается. Если backend не позволяет отключить физику, BE, взаимодействия и выдачу предметов для кандидата до тиков, восстановление выполняется до запуска мира либо запуск затронутого измерения блокируется.

## Стабильная привязка Universe → Sable

Отдельный `NativeShipBinding` содержит `worldId`, `ShipId`, `bindingEpoch`, `backendId/version/hash`, native UUID, ключ измерения, адрес plot с поколением выделения, `lastTransferId`, состояние `ACTIVE / TRANSFERRING / BLOCKED`, ревизию метаданных. Plot — адрес хранения, не постоянная идентичность; освобождённый адрес нельзя повторно признать тем же кораблём. Связи стыковки используют `ShipId` и стабильные Universe port ID, а native ссылки пересчитываются после проверки назначения.

Обратный индекс `(worldId, backend, dimension, native UUID, plotGeneration) → ShipId` обеспечивает уникальность. Предыдущая привязка сохраняется tombstone с эпохой и operation ID, чтобы поздний callback не оживил source. Обновление выполняется сравнением ожидаемой эпохи; сообщения старой эпохи отвергаются. Координаты, одинаковый корпус или близость к точке назначения не являются доказательством принадлежности.

У Sable 2.0.5 исследование подтвердило `getUserDataTag/setUserDataTag`; собственный backend должен явно записывать кандидату `ShipId`, `transferId`, целевую эпоху и роль `TARGET_CANDIDATE` в namespaced compound. Наличие API не доказывает durable-порядок сохранения этих тегов. Dimensional-Sable их перенос явно не выполняет; SablePortLibrary копирует userData, но ссылки внутри требуют адаптера. Если выбранный backend не обеспечивает метки, допустим только проверенный внешний индекс с доказуемой связью с конкретным native объектом. Если новый UUID невозможно устойчиво сопоставить операции после сбоя, автоматическое восстановление запрещено.

Существующий `ShipCatalog` хранит позу и сводки, но не журнал исполнения, backend-привязки и подтверждения записи. `setDirty()` не является durable barrier. Эти возможности потребуют отдельной схемы; данный документ не меняет существующий код.

## Durable journal

Журнал располагается отдельно от чанков и `ShipCatalog`, например `universe/transfers/`. Запись содержит схему, монотонный номер, `transferId`, stable ID, ожидаемую эпоху, source/target descriptors, этап, предыдущий hash и checksum. Числа, строки, число членов группы и размер записи ограничены. Полные блоки, BE NBT и меши в журнал не помещаются; при необходимости он ссылается на отдельный проверенный снимок или согласованную резервную копию.

Предлагаемые этапы: `PREPARED → EXECUTING → TARGET_DURABLE → COMMITTED → SOURCE_RETIRED → DONE`. Любой этап может перейти в `BLOCKED`; `ABORTED` разрешён только до вызова backend при доказанно нетронутом source. `EXECUTING` означает неопределённый результат: запись создаётся и подтверждается на диске ДО первого побочного действия.

Повтор входящего `transferId` с тем же каноническим запросом возвращает текущий результат журнала; тот же ID с другим назначением, эпохой или составом группы отвергается. Это идемпотентность запроса Universe, а не гарантированная идемпотентность backend. Истечение lease освобождает только неисполненную резервацию; операция `EXECUTING` не повторяется по тайм-ауту. На один корабль разрешена одна незавершённая операция. Первоначальные лимиты проекта: 16 одновременных операций, до 16 участников будущей группы, запись до 64 КиБ; фактические бюджеты проверяются стендом. При заполнении хранилища новые операции отвергаются, незавершённые записи и tombstones не вытесняются.

Переход этапа дописывается и выполняет `FileChannel.force(true)` перед следующим действием. Ошибка записи/flush останавливает перенос. Нельзя переписывать старую запись на месте. После сбоя читается корректный префикс; неполный хвост блокирует затронутую операцию. Контрольная сумма обнаруживает повреждение, но не заменяет сохранность носителя. Атомарная замена контрольной точки допустима только после проверки файловой системы; переносимые гарантии устойчивости rename и каталожной записи отдельно не предполагаются. Контрольные точки и tombstones не удаляются, пока backend и каталог не согласованы.

Этот журнал обеспечивает восстановление решения Universe, но не атомарность нескольких vanilla/Sable файлов. Реальная точка `TARGET_DURABLE` требует backend-подтверждения сохранённого объекта и завершённых зависимых записей либо согласованного остановленного checkpoint мира, чья пригодность проверена повторной загрузкой. Обычный автосейв и временная задержка не доказывают такую точку.

## Порядок безопасного переноса

1. На серверном потоке захватить эксклюзивную операцию для `ShipId` и эпохи; запретить движение, редактирование, контейнерные операции, шлюзы и новые переходы. Клиент не определяет UUID назначения и состав группы.
2. Провести preflight: source принадлежит привязке, destination существует и допустим, место зарезервировано, содержимое и отношения поддержаны. Доказать загрузку всех нужных chunks plot: Sable `plot.save()` сериализует загруженные chunks, поэтому неполный снимок недопустим. Проверить `log_size`, minY/height и полный диапазон занятых секций назначения до allocation. Закрыть интерфейсы контейнеров и завершить либо остановить операции предметов. При невозможности заморозить стороннюю систему отказать до backend.
3. Создать проверенный согласованный checkpoint или доказуемый backend-снимок, записать `PREPARED`, затем `EXECUTING` с durable barrier. Зафиксировать policy совместимости и хэши зависимостей.
4. Вызвать backend один раз. На исключении оставить `BLOCKED`; не повторять запрос автоматически. Новый native UUID/plot записать как кандидата, ещё не активную привязку.
5. Проверить полноту target: секции, палитры, BE, предметные компоненты, жидкости, запланированные ticks, связанные сущности и отношения согласно поддерживаемому контракту. Контрольные суммы рассчитываются для согласованного снимка; нормализованные позиционные поля проверяются по правилам fixers. Сводные массы и количества блоков сами по себе недостаточны.
6. После доказанного сохранения target записать `TARGET_DURABLE`, затем `COMMITTED`: журнал становится источником решения о новой эпохе. Каталог — восстанавливаемая проекция этого решения; обновление отдельного `.dat` не объявляется общей транзакцией.
7. Только теперь разрешена проверенная backend-очистка source. Отсутствие API безопасного удаления означает удержание source в карантине. Записать `SOURCE_RETIRED` после подтверждения его неактивности/устойчивого удаления. Активировать ровно один target после сверки привязок и записать `DONE`.

Для одностадийного разрушительного `WarpSubLevel` пункты 4–7 могут оказаться недостижимы: если source удаляется внутри вызова, проверка пункта 5 происходит слишком поздно. В этом случае функциональность не включается. Нужен другой проверенный backend, подготовка/commit API либо upstream-изменение. Полная резервная копия позволяет восстановить мир целиком, но не превращает этот вызов в транзакционный перенос.

## Восстановление до допуска игроков

Восстановитель проверяет журнал, backend-сохранения и индекс, включая выгруженные объекты. Отсутствие объекта среди загруженных sub-levels не равно отсутствию на диске. Если перечисление сохранений не поддерживается, результат «не найден» считается неопределённым. Неподтверждённые объекты замораживаются до тиков; если это невозможно, сервер не открывается игрокам.

| Состояние журнала и наблюдения | Действие |
| --- | --- |
| `PREPARED`, только проверенный source, backend не вызывался | Отменить до исполнения; source разблокировать после проверки |
| `EXECUTING`, только source | Не повторять warp; проверить следы target, иначе карантин |
| `EXECUTING`, source и target | Обе копии закрыты; target не становится активным без durable-проверки и доказанной принадлежности |
| `EXECUTING`, только target | Проверить восстановимость и полноту; отсутствие source не считать успехом |
| `TARGET_DURABLE`, ровно один подтверждённый target | Продолжить commit после проверки checkpoint; source пока карантин |
| `COMMITTED`, target подтверждён, source ещё существует | Восстановить новую привязку из журнала; source неактивен; очистка отдельным проверенным шагом |
| `COMMITTED`, target отсутствует или повреждён | `BLOCKED`; source не активировать автоматически, возможны уже выданные целевые состояния |
| `DONE`, совпали эпоха и target | Допустить единственный объект после обычной валидации |
| Ноль объектов, несколько targets, разрыв checksum, конфликт эпох | Заблокировать; сохранить доказательства и восстанавливать согласованную копию |

Разблокирование после аварии требует сверки сохранённого состояния, а не тайм-аута. Восстановление checkpoint выполняется на остановленном сервере для всех затронутых файлов; выборочное возвращение сундука или playerdata способно дублировать груз. Журнал выводит для оператора отчёт с operation ID, этапом, кандидатами и причиной блокировки, но не выполняет эвристическое удаление.

Пассажиры и стоимость перехода имеют отдельные связанные записи с тем же `transferId`; native перенос корпуса не считается переносом playerdata. До выполнения требуется подтверждённый способ удержания пассажиров в безопасном месте. До `COMMITTED` предметы не выдаются целевой стороной. Если баланс топлива или внешняя система торговли не поддерживает резервирование/идемпотентное списание, переход с этой системой отключается. Поздний reconnect восстанавливает игрока только после проверки эпохи и активного владельца; неоднозначный корабль не становится местом входа.

## Неподдерживаемые BE и connected groups

Политика первой интеграции — allowlist проверенных типов BE и entity данных, привязанная к версиям модов. Неизвестный тип отклоняется до переноса, даже если его NBT выглядит простым. Проверяется не только наличие BE, но и активные contraptions, движущиеся поршни, внешние координатные ссылки, capabilities/attachments, inventories и loot. Fixer должен быть проверен для каждого изменяемого поля; универсальный поиск UUID в NBT недопустим. `SubLevelTeleportStateAdapter.capture/restore` SablePortLibrary не является prepare/commit/rollback API: ошибка restore уже следует за удалением источника. Такой адаптер не закрывает требования восстановления.

Первый безопасный режим допускает одиночный объект без connected groups. Проверяется замыкание физического графа: docking, rope, spring, ground anchor и внешние механизмы. Исследование установило, что перегрузка `warpConnected` у Dimensional-Sable private; Universe не может считать одиночный публичный вызов доказанным. Family SablePortLibrary определяется эвристическими UUID-ссылками и не доказывает полноту физического графа. При неизвестном графе или прикреплении к земле перенос отклоняется. Открытые шлюзы, незавершённые пассажирские/грузовые операции и активная стыковка также блокируют перенос.

Будущая поддержка группы требует одного durable operation ID, полного списка участников со stable/native ID и эпохами, общего checkpoint, проверки target каждого участника и всех рёбер. Частичный успех оставляет всю группу заблокированной. Если backend рекурсивно переносит неизвестный набор объектов, Universe не может безопасно принять его результат.

## Критерии допуска backend и испытания

До включения на основном мире требуется доказать через источник и серверный эксперимент: порядок удаления source; сопоставление новых UUID/plots; обнаружение сохранённых кандидатов; заморозку до тиков; устойчивость подтверждения target; поведение исключений; поддержку выбранных BE и графа. Неуспех любого пункта оставляет интеграцию в исследовательском режиме.

Crash-injection выполняется до/после каждого journal barrier, каждого backend-побочного действия, записи target, commit и очистки source; дополнительно испытываются kill процесса, усечённый журнал, нехватка диска, неподдерживаемая схема и исчезновение зависимости. После запуска доступны ноль или один корабль; никакой неподтверждённый объект не тикает и не выдаёт предметы. Проверяются сохранность груза/BE, playerdata, UUID и отсутствие повторного вызова backend для операции в неопределённом состоянии. Отдельно измеряются лимиты журнала и время поиска объектов.

Связь с `SABLE_VALIDATION_MATRIX.md`: U05, G06–G09 проверяют применимое восстановление. Формулировка «rollback» в сценарии не разрешает вызывать обратный warp; при отсутствии подтверждённого механизма ожидаемый безопасный результат — карантин и диагностируемый отказ. Такой результат подтверждает безопасность отказа, но не закрывает успешный gameplay-перенос G01–G03.

Итоговое ограничение: exactly-once эффект переноса недоказуем одним внешним журналом, если backend не предоставляет идемпотентность или обнаружение результата. Universe обеспечивает запрет повторного неопределённого вызова и блокировку неоднозначных владельцев; атомарность физического переноса остаётся условием допуска backend.
